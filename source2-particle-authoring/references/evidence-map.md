# What the bundled evidence proves

Use this reference when deciding whether a field, behavior or example is
established, or when reviewing the package. Ordinary authoring needs only the
relevant contracts and a test of the requested effect.

## The data is a reference, not a particle simulator

The schema catalogue is generated from a pinned public CS2 SchemaExplorer
snapshot. The control-point catalogue selects related declarations and their
dependencies from that data. The archive observations come from decoded
native CS2 and Deadlock VPK resources. They are not equations or support
lists inferred from a web preview renderer.

A tool's ability to display a class is separate from the native engine's
ability to use it. Conversely, a real engine field can be reflected without
being an editable VPCF key. Preserve serialization metadata, exact provider
types and the evidence's target game.

## Reviewed coverage

These counts describe the distribution reviewed on 2026-10-20. They do not
require that game build or promise the same catalogue for every Source 2 game.

| Evidence | What was checked | What it does not establish |
| --- | --- | --- |
| Schema snapshot | All 464 selected classes, 3,001 declared fields, 10,921 own/inherited field occurrences, 92 enums and 512 members were reconciled with the exact upstream snapshot. | Runtime formulas, editable-field acceptance, visual results or all possible combinations. Many default chains are partial or unavailable. |
| Control-point snapshot | 213 selected classes and 62 enums retain their typed declarations and dependencies. | A working attachment, live update, coordinate convention or parent/child mapping for an arbitrary authored effect. |
| Archive observations | 427 class/stage records contain 58,113 observed field paths across two separate game corpora. Each field retains a bounded example and source identity. | An exhaustive engine schema, a property default, an allowed-value range, or identical behavior between games. |
| Native editor help | 22 behavior facts are traced to exact Valve-authored help passages. The schema help index has descriptions for only 139 of the 3,001 declared fields. | A description for every property, or a measured implementation of every documented statement. |
| Controlled behavior fixtures | 13 historical native compiler/readback checks retain their source and output identities. | Runtime or pixel verification; that ledger explicitly records neither. |
| Native recipe observations | Selected material, model, refraction, motion and timing findings are documented with their actual setup and limits in the specialist references. | Class-wide certification, automatic gameplay integration or a performance guarantee. |
| Portable helper tests | Offline queries, source identities, bounded extraction, orchestration and failure reporting. | Native engine execution or artistic quality. |

The reference-research skill records a correction to historical numeric
extrema: the original aggregate skipped some decoded integer values. Those
minima/maxima are withdrawn. Examples and frequency evidence remain useful,
but observed values must never become an authoring range restriction.

For detailed provenance and verification commands, use the installed
`source2-particle-schema`, `source2-particle-control-points`,
`source2-particle-reference-research`, `source2-particle-behavior` and
`source2-particle-validation` skills as needed. Their evidence files identify
the source snapshot, resource or native run. A hash proves identity, not
correctness by itself.

## A useful claim follows its evidence

For a new field, obtain its exact type and serialization metadata. Read a
relevant native help passage or game-resource example when one exists. Use a
controlled nondefault value to test native compiler retention. Observe the
specific behavior in PET or the intended game scene before calling it tested.

For example, a retained CP index proves serialization of that reference.
Moving the CP after emission can test whether existing particles follow it.
Spawning through the real game attachment API tests a further integration
claim. None of those steps establishes unrelated CP consumers.

Use established, relevant observations without repeating an entire audit for
every effect. Investigate a changed field, failed compile, decoder mismatch or
visible regression when there is evidence of one. Build identifiers date
observations; they are not version locks.

## Keep the first task small

Begin with the requested effect and its production CP contract. Search for
classes, discover a bounded field page, then query the exact fields being used.
Batch fields from the same class. Read additional references when a concrete
mechanism or failure requires them.

For a new contributor, the useful final result is an editable root, its required
children and resources, explicit CP initialization, and the checks actually
completed. Large catalogues support those decisions without being copied into
the conversation or the delivered addon.
